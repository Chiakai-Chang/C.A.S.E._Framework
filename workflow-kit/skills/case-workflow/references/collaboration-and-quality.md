# 分工、整合與驗收

單 agent 能直接完成就直接完成。當有兩件可独立推進的工作、需要不同專業判斷或盲點審查，而且宿主能力及授權允許時，才分工。不要為了 MECE 列滿角色；按實際風險確保必要面向有負責人即可。

## 發出工作包

指定成果、驗收、必要輸入、可改檔案／副作用、不能改的約束、回報長度，以及何時停止。可使用 [範本](../assets/task-notes.md) 的 worker 段落。各 worker 只讀完成本身工作所需資料，不繼承所有歷史。

協調者是任務狀態的唯一寫者；worker 不修改 `.case-agent`。若會修改產物，分配互不重疊的檔案或使用宿主提供的隔離工作區。單純分配檔名不是鎖或隔離保證；重疊工作先串行整合。worker 發現越界需求先回報，不自行擴大權限。

`handoff` 僅寫接手資訊；實際派工、送訊息或建立 session 使用宿主提供的功能與既有授權。宿主不支援 subagent 時，協調者依序完成工作包即可；不要宣稱執行了獨立審查。

## 收斂不同意見

每個回報提供結論、產物引用、已執行驗證、未解限制及建議下一步，保留失敗。協調者檢查關鍵產物並將建議對照原驗收，不直接投票或把多 agent 同意視為證據。

有衝突時定位造成分歧的事實或取捨，只研究能影響決策的缺口。一般技術選擇自行決定；需要使用者價值取捨或新權限才詢問。結果已有充分依据就整合，不加一輪對稱審閱。採用與未採用的重大意見可各用一句記錄原因。

## 驗收與交付

以真實產物核對 criterion。程式修改執行相關測試；文件核對事實、連結與閱讀路線；安裝流程在隔離專案驗證；需要人確認的體驗不能由程式測試代替。測試通過不自動代表全產品有效。

證據寫可定位的來源與觀察，例如「執行 node --test tests/export.test.js，3/3 通過；涵蓋逗號、雙引號與換行」。若結果未執行或來源無法確認，就保留 pending 或記 fail 與原因，不製造 pass。

完成時回報使用者可取得的成果、使用入口、完成程度與影響使用的重要限制。明確區分：程式有實作、特定環境跑過、真實使用收益已觀察；不能由第一項推論第三項。只有實際發現可改善後續工作的經驗才記簡短復盤，沒有新資訊不新增文件。

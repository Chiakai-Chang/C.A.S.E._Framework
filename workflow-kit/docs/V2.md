# v2：交辦、回饋與接續

v2 是目前的預覽實作。你交代要什麼成果，框架把長期共識、本次計畫、當前執行材料分開，並把執行中的缺口送回規劃者。pi 可自動用新 session 完成這個循環；其他工具共用核心資料及交辦方法，不等於已自動互相指揮。短工作仍直接做，不強制分工；分離 context 有額外成本。

## 選擇入口

目前不建議因為工作有多個步驟或檔案，就預設啟動完整分工。[固定版比較](../../docs/evaluation/case-value-validation-report.md)未顯示品質優勢，且出現 worker 自稱已寫入但沒有產物的失敗。直接完成或良好摘要接續優先；需要來源版本、相依工作包與獨立核對紀錄時再明確選用此預覽流程。以下範例示範能力，不代表簡單資料整理一定值得分工。

| 需求 | 入口 | 實際能力 |
|---|---|---|
| 輕量記錄與手動接續 | `case.mjs`、[v1 實例](WORKFLOW.md) | agent 自行工作，CLI 保存狀態 |
| 版本化契約／工作包 | `case-v2.mjs`、[技能參照](../skills/case-workflow/references/v2-contracts.md) | 核心檢查相依、來源版本、核對及整合條件 |
| pi 自動新 session | pi package 的 extension、`case_workflow` | 沿用已選模型，依序執行各階段 |
| Codex／Claude Code／Antigravity | 可攜技能與同一核心 | 可讀寫卷宗；本套件未提供其自動 session 整合 |

安裝見 [HOSTS](HOSTS.md)。Skills 或 `install.mjs` 只複製技能及核心；pi package 才包含 extension。兩者不要疊裝同名技能。原生本機套件安裝驗證狀態以 [READINESS](READINESS.md) 為準；尚未驗證的 Git 遠端安裝不作推薦入口。

## 在 pi 交代工作

先選定預期模型，需要本地執行時確認 provider 指向本地服務。對 agent 說明需求，例如：

> 用 CASE 整理專案 CSV，保留原始檔，產出可核對筆數與加總的摘要。把工作拆到足夠完成即可，總時間最多五分鐘。

agent 呼叫 `case_workflow` 的 create，從要求建立 `goal`、有穩定 ID 的 `constraints`／`acceptance`，以及 `budget.maxAttempts`／`maxDurationMs`；完整 JSON 範例在技能參照。需要更長預算或改用其他模型時，由原授權範圍判斷，不默默擴大。

```text
/case list
/case show <回傳的id>
/case run <回傳的id>
/case stop
```

create 是 agent 工具操作，不是 `/case create` 指令。run 使用最少必要工作包依序執行，不會平行啟動多個 worker。worker 只能寫指定產物範圍，其他階段使用讀取工具；新 session 不繼承 worker 聊天，但仍依 pi 載入專案指引。這不是作業系統隔離。

各子 session 透過 `case_result` 傳送結構化回報，聊天文字與正式資料分開保存；回報接受後不能再操作工具。worker 提交前會查實際產物及本包已核准檢查，遭拒仍可在原 session 修復再交回。這不是跳過核心或獨立驗收。工具只由框架內部使用，一般使用者不用操作。

契約可指定 `writeScope` 為本次授權的檔案／資料夾上限；規劃者只能在內拆包。不要將模型自行列出的範圍當成新授權。

## 大憲法、小憲法如何落地？

| 層次 | 保存內容 | 實際位置 |
|---|---|---|
| 專案共識（大憲法） | 長期目的、限制、既有指引的版本引用 | workflow.json 的可選 projectPolicy |
| 整體工作 | 本次成果、驗收、預算及可修正計畫 | 卷宗 contract、packets 與變更歷程 |
| 當前交辦（小憲法） | 必要限制、材料、相依、允許改動及檢查 | 從同一狀態組裝的 packet context |

不新增通泛的根目錄檔名，也不要求人同時改 JSON 與 Markdown。跨任務需要共識時，請 agent 依既有要求整理設定，檢查後使用：

```text
/case project "project-policy.json"
/case project
```

第一行會顯示確認內容；第二行只查看。設定範例為 `{"summary":"本機完成可追溯報告","constraints":[{"id":"local","text":"資料不外傳"}],"sources":["AGENTS.md"]}`，sources 只能列真正存在的指引。新卷宗繼承快照；來源變更後要重新確認共識，並明示 revise 舊卷宗，不能自動放寬。一次性的工作可不設定此層。

## 遇到問題如何繼續？

- 原包產物有缺陷：先在原 session 自查、修復；提交預檢拒絕時依具體錯誤繼續修正。之後獨立核對仍失敗，才帶核對證據用新 context 修復。
- 執行中發現新工作：立即用 `case_discover` 保存證據及影響。nonblocking 保存後繼續；blocking 暫停本包，由規劃者在原授權內去重、補前置及調整相依。提案不是直接改計畫，不需要 GitHub Issue／PR。
- 外部資料或新授權不足：規劃者將發現標成 needs_input，只有受影響工作等待，獨立包繼續。條件未變時接續不重複呼叫規劃者；補足後明示 reopen_discovery 再接續。
- 缺可由現有材料補做的前置：worker 回覆 changeRequest，規劃者補包，核心核對相依與授權，再續作。
- 執行者遇阻：回覆 blocked 或 changeRequest，保存原因並交回規劃者；規劃者依完整契約判斷可否補做。真正缺外部資料或新授權時，規劃者回覆 blocked 停止，不捏造。兩種回饋共用原有重規劃上限。
- 各包通過但整體不合格：帶整合失敗回到規劃者，必須補做後再驗收。

修正計畫使用 `amend_plan`，不改目標／驗收／預算；未受影響且版本有效的已核對包保留，寫入重疊及相依受影響的部分重做。舊終止回饋最多兩次自動重規劃；新待辦由 `resolve_discoveries` 將處置與補包一次保存，不占這兩次額度，但仍受原始時間／session／attempt 預算限制。需要改目標、新權限或新增預算時才交回使用者決定。完整狀態、去重及解除阻礙操作見[執行中發現參照](../skills/case-workflow/references/v2-contracts.md#執行中發現與待辦處置)。

## 執行真正的測試／檢查

檢查工具也依階段分配：planner 不取得檢查工具；worker／reviewer 只取得 `criterionIds` 與當前工作包相符的檢查；integrator 取得全部。未指定 `criterionIds` 的整案檢查不交給前置工作包，避免因下游產物尚未建立而誤判失敗。

請 agent 依專案準備檢查設定，例如 `{"tests":{"command":"node","args":["--test"],"timeoutMs":30000}}`，然後由你執行 `/case checks <FILE>`，看清命令與程式後確認。runner 在全域整合執行清單，保存 exit code 與輸出；失敗不能被模型 passed 覆蓋。若加 `criterionIds:["a1"]`，涵蓋該驗收的工作包也會執行。

此授權包含命令執行的專案程式，具有目前使用者權限，不是沙箱。不可信程式應另行隔離。清單只留在當次 extension 記憶體，重開後要重新確認；`/case checks-clear` 清除後續授權，執行中需 `/case stop`。沒有清單仍可做來源／內容核對，但不宣稱已跑測試。模型不能自行新增命令。

## 保存與接續

工作包材料與 pi 工具共用受保護路徑規則：任何層級的 `.case-agent`、`.git`、`.pi`、`.agents`、`.codex`、`.claude` 不作工作材料，大小寫不影響判斷。一般 `AGENTS.md` 仍可作已選的指引來源。舊工作包若含這些設定目錄也會拒讀，需明示調整材料／計畫，不能靠 inline 載入繞過工具限制。這不是完整的秘密掃描或作業系統沙箱。

待辦也需要 context 管理：規劃、整合及當包只收到發現索引，完整證據與處置歷史透過唯讀 `case_discovery_read` 按需分頁，不把所有歷史塞回每個 session。索引有明示截短標記，不是忽略必要證據；讀取範圍與當前角色／卷宗綁定。詳見[發現與接續參照](../skills/case-workflow/references/v2-contracts.md#執行中發現與待辦處置)。正式回報被接受後由程式直接停止生成、交回外層，不依賴模型再自行說結束。

pi 的計畫回報先用核心規則預檢；缺驗收項目、無效相依或越權等錯誤會留在原 session，讓規劃者依具體原因修正，尚不提交狀態。正式提交仍重新檢查版本與來源。若 session 結束時只有說明文字、沒有可接受的結構化回報，runner 在原回合／時間預算內最多補問一次；取消、回合用完或已收下回報時不補問。這不是重做工作，也不放寬驗收；補問原因與原回覆保存在 `replyCorrections`。

寫入工具紀錄另保存 `writeRequest.path` 與該 session 的 `writeRequest.writeScope`，失敗或取消時也保留，便於判斷拒寫原因；不因此保存寫入內容。舊紀錄缺少這些欄位時表示未知，不能回推當時要求的路徑。

`.case-agent/workflow.json` 記錄 `case-workflow/2`；`cases/<UUID>/state.json` 是每個卷宗的唯一權威，含 discoveries 待辦及處置。啟用佇列後該 state 使用 `case-workflow/2.1`，新版讀 2／2.1，舊版拒絕新格式；共同操作的核心應同步更新。`artifacts/` 保存 run 回報、模型／session 資訊、用量及工具觀察。缺少用量記 unknown／null，不能當作零。來源、產物以 SHA256 綁定，不只保存 worker 自述。

工作包經 running、submitted、verified；提交不等於核對通過。所有必需包有效且全域驗收逐項通過才 completed。`context` 帶全域限制及必讀資料，超過 `maxChars` 報錯，不默默截斷；字元不是精確 token。大型必要材料可設 `delivery:"indexed"`，保留版本與必讀義務，透過 read 分段取得；不是隱藏限制，也不是忽略資料。現有 read 單檔上限 1 MiB、每次 200 行／24000 字元；超過須另外安排有授權的前處理。

中斷後先 show，查看 run artifacts 與部分成果。仍 running 時先確認原程序已停止，不盲目重播；`stop` 只是取消請求。必要材料不足而無法規劃時，planner 可回覆 `{blocked:{reason}}`，runner 保留非空原因、回報 BLOCKED 並停止，不啟動 worker。需修正時用 retry 保存原因，runner 會保留有效 verified 包並接續待核對／待執行工作。契約變更用 revise 後重新 plan；全部舊核對保守失效，累計預算不重置。完整操作與 CLI action 介面見技能參照。

## v1 升級

v1 `case.mjs` 保留。先停止寫者，有明確升級意圖後才執行：

```text
node "<skill-dir>/scripts/case-v2.mjs" migrate --project "<project>"
```

migration 在 `.case-agent` 外產生備份，驗證後才切換格式；保存回傳 backupPath。舊 tasks 保留歷史，續作另建有來源關聯的新卷宗，不把舊完成紀錄轉成 v2 獨立驗收。遷移後 v1 拒絕寫入是保護。升級技能與遷移資料是不同操作；更新／移除技能不刪卷宗。

## 證據與限制

真實本地模型的 CSV 單 context 與分離流程已有 smoke 成功，也在重複配對觀察到分離流程的整合回覆錯誤。開發結果已保存在 repository 的 `docs/evaluation/case-v2-local-report.md`；修正前後不是固定版本統計，尚未證明品質提升或成本節省；另有跨檔案資料彙整、缺資料安全停止及保留上游接續各一次核對通過；原生安裝、執行與移除已實測且保留卷宗／產物。缺料提示的後續修正與原始結果分開保存。長工作及不同模型效果仍需驗證。測試與平台範圍集中在 [READINESS](READINESS.md)。[English guide](GUIDE.en.md#v2-preview-contracts-and-fresh-sessions) 提供對應說明。

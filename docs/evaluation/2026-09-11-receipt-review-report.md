# 核對引用由程式解析，而不是模型重抄

日期：2026-09-11。接續[正常完整任務及引用缺陷](2026-09-11-worker-grounding-report.md)。使用者同意改進回報介面；目標仍是有限 context 下把工作做好，減少核對錯誤與人的追查負擔。

後續：[不同正常任務](2026-09-11-holdout-journey-report.md)已實測，出現有效引用仍誤驗完成的反例；不能把本頁局部成功擴大成整案可靠。原紀錄與成本保留。

## 根因與取捨

上一案工具已正確回傳來源、行段及 SHA256；錯誤發生在 reviewer／integrator 重述行號與雜湊時。原本 evidence 接受自由文字，材料門檻只確認讀過目前版本，沒有核對敘述中的引用。再加紀錄或精準提醒，不能修正此邊界。

採用模型提交判斷理由及讀取回條 ID，由程式補齊 metadata。不採用自由文字正則掃描（無法可靠解析語言），也不新增引用工具或另一位審查者。不改目標、權限、角色數、自查／回饋與原總預算。

## 行為與相容性

- `case_read` 新增 `receiptId`，文字與 details 一致；仍遵守含回條在內的 24,000 UTF-16 字元上限，正文與行段語意不變。
- 正常 pi runner 的 reviewer／integrator 使用 `evidenceMode: "read-receipts"`。模型的 evidence 為 `{assessment, receiptIds}`；成功主張至少一個引用，失敗可用空陣列說明缺料，每份 evidence 最多 16 個不重複 ID。
- SDK 只接受本 session 有效範圍或空檔讀取；拒絕捏造、範圍外、過期及已刪除來源。搜尋供定位，不能冒充讀取回條。模型不能在結構化 evidence 另填 path、hash 或行號。
- 接受後為 `{assessment, citations}`，citations 是程式保存的實際回條，附完整來源／結果 SHA256、路徑、行段及範圍旗標。原始提交保存為 `rawResultText`，原最後文字仍在 `rawFinalText`；成功及失敗 run 均支援保存。
- 工具與最後文字走相同檢查，格式修復不增加額度。獨立審閱指出舊錯誤訊息會教模型交回不相容字串，已修正並加回歸；legacy 最後文字保留原始空白。
- 共用核心、CLI 與卷宗不遷移。直接呼叫 SDK 預設 legacy；自訂 session transport 必須自行驗證證據，不把可攜核心接受 evidence 當成替外部工具核實引用。

**界線：** 程式解析來源不保證語意正確。模型仍可能引用無關段落、在 assessment／findings／summary 寫錯，或漏掉條件。回條行段是實際讀取範圍，不等於精確支持句；獨立判斷與可信 checks 仍必要。

## 驗證

缺失行為先紅後綠，再接入 runner；補上格式修正、legacy、空檔、跨 session ID 及刪除來源反例。完整 kit：**335 項，333 通過、2 項 Windows 符號連結權限跳過**。獨立審閱的格式指引缺陷已修正，限定複核無剩餘阻擋問題。測試不等於模型效果。

交付核對：257 個本地文件連結目標存在（未驗所有標題錨點）；實測 6 個引用逐一符合工具回條、來源雜湊及返回行段。封裝預覽 37 檔，包含新模組、不含快取。全域 npm 預覽因既有 npm-bundled 缺檔失敗，改用 `C:/Program Files/nodejs/node_modules/npm/bin/npm-cli.js` 完成；未重建 npm、pi 或 AppData，也未發布套件。

[原始證據](2026-09-11-receipt-evidence.json)及[執行腳本](2026-09-11-receipt-probe.executed.mjs.txt)：新建三份短文件，政策要求超過 5 天才逾期、移交恰為 5 天且有備份，預建評估卻寫逾期。只啟動一個真實 integrator，分別判斷逾期與備份，不向模型回饋標準答案。

**42.792 秒、10,066 SDK 累計 tokens**（input 3,574、output 810、cacheRead 5,682）；正確判定逾期不合格、備份合格，兩項都引用實際三份讀取回條。5 次完成工具觀察：1 list、3 read、1 result；沒有工具錯誤或壓縮，trace 完整，來源未變、無額外檔案。服務及全域 pi 未修改。

這是預建錯誤成果的單獨整合診斷，不是正常整案、修復成功率或成本比較。同模型 ID、off／32768／4096、8 回合及 120 秒獨立上限，未延長舊卷宗。保存服務 props，但 seed、cache、GGUF 位元組、峰值 context 及硬體成本未控制。成本與上一批 575,000 分開。

診斷期間程式雜湊不變；**完成後才修正格式錯誤指引及 legacy 文字保留**，這兩項由回歸驗證，不冒充同一次模型實測。證據使用基底雜湊及差異清單保存版本；公開 JSON／腳本與本機內容一致，僅檔尾換行正規化。腳本原位於 `.npm-cache/`，不是安裝入口。

## 成本復盤

唯讀分析[上一案紀錄](2026-09-11-worker-assignment-journey-evidence.json)，沒有再呼叫模型：

| 角色 | 成功 read 次數 | 讀取正文字元 | 同 session 重複正文 |
|---|---:|---:|---:|
| planner | 5 | 18,900 | 0 |
| worker | 15 | 29,415 | 8,540 |
| reviewer | 6 | 20,875 | 0 |
| integrator | 6 | 20,875 | 0 |

只取成功且有 range 的 case_read，移除首行回條，按正文行計 UTF-16 字元（不含換行）；各 session 以 path＋sourceSha256＋行號去重。另有一次失敗 read，搜尋及其他工具不在表內。worker 重複正文約 29.0%，含局部核對，不能直接當成浪費刪除。跨角色亦不能用別人的已讀來冒充獨立核對。

上一案 454,646 tokens 為 input 61,614、output 8,199、cacheRead 384,833（約 84.6%）。這不是 45 萬 token 同時佔用 context，也不是全部重新生成；不能據此推算耗時、硬體成本或省略核對的收益。

下一步：直接完成仍優先；需要分工時，以不同正常任務確認新介面不阻塞生命週期，再判斷可省的規劃查讀與重複資訊。沒有擅自省略核對、強加短回覆限制或宣稱節省幅度。回看[原始分層構想](../research/2026-09-05-layered-cooperation-direction.md)，框架應讓責任與材料清楚、可接續；來源識別由工具處理，不把負擔轉成人工比對雜湊。

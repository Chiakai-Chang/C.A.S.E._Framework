# pi 重建後的 CASE 核心修復

日期：2026-09-06。接續[原四次失敗](case-feedback-report.md)與[pi 重建](../research/2026-09-06-pi-clean-rebuild.md)。目標仍是本地模型完成正確成果，不以測試數或安全停止替代成功。這是開發診斷，不是固定版本效果比較。

## 已查明並修正

1. **工具提示接線**：pi 0.84.2 使用 `promptSnippet` 產生 system prompt 的工具清單。CASE 只給 description，導致工具 schema 存在，文字提示卻說沒有工具。現在由實際工具定義同步產生提示。
2. **模型設定接線**：SDK registerProvider 要把 compat 放在個別 model；models.json 的 provider 預設不能直接照搬。探測現在記錄送出前的 thinking 模板參數與 token 上限。這是探測設定修正，不把 Qwen 專用參數寫入通用 runner。
3. **回饋責任**：worker 的 blocked 是障礙回報，不是外部缺料的最終裁定。現在 blocked／changeRequest 都交給 planner 分類；真正缺外部資料仍停止，不擴張授權，最多兩次重規劃且沿用總預算。
4. **計畫格式**：模型曾填 `delivery:"default"`；有效值其實只有 inline／indexed。修正說明並在原生工具 schema 驗證，使模型能在同一 context 修正無效工具參數；完整計畫仍由核心驗證。
5. **檢查分配**：原先把需要下游 report 的整案檢查也交給前置 worker，模型寫出正確 normalized 後反而被檢查引向越權補寫與重規劃。現在 planner 無檢查工具、worker／reviewer 只取得對應 criterionIds 的檢查，integrator 取得全部；模型不能覆蓋真實檢查失敗。

各項行為修正有先失敗再通過的回歸測試；截至第 10 次診斷，完整 Kit 測試 113/113 通過。後續修復見下節，最新完整回歸 119/119 通過。這只證明工程規則，不證明模型可靠度。

## 目標復盤與接續

原始構想的價值在分清規劃、執行、核對及回饋責任，不在增加角色或文件。這輪修復消除的是框架自己製造的混淆；不能用提高權限、忽略驗收或重試到成功補足證據。

第 9 次保持任務、工具、核心程式與預算，僅在隔離探測將 thinkingLevel 從 off 改為 medium；payload 確認 enable_thinking:true。已產生兩份正確成果且外部精確值檢查通過，但整案未結束；一組觀察不能建立因果或可靠度結論。第 10 次另開新案，保持此設定，只把總時間從 240000 改為 600000 ms，以容納已觀察的逐階段生成時間；不是重置第 9 次既有卷宗的預算。

重現思考診斷：在 `feedback-probe.mjs` 的同目錄建立暫時副本，把 evidence.configuration 的 thinkingLevel 改為 medium，並在 createPiSessionRunner 參數加 `thinkingLevel:'medium'`；其餘保持不變。摘要另附實際診斷副本 SHA256；codeHashes 的 feedback-probe.mjs 仍指正式 off 版，不誤稱它就是實際執行副本。這不改使用者全域 pi 設定，也不將 medium 當成已驗證的最佳值。

pi 重建備份仍保留；沒有刪除 AppData、模型、舊 harness 或備份。刪除備份需先列明精確目標與方法，再取得使用者確認。

截至第 10 次的結論：全域 pi 已可正常使用；CASE 接線與分層責任有已驗證的工程修正，但新回饋流程仍未驗收。當時下一步是補上必要的失敗參數觀察（工具名稱、要求路徑、允許範圍，不收集寫入內容），先用單一 report 工作包定位；該階段診斷副本已移除，全部探測與產物保留。以下接續，不改寫前十次失敗。

### 已證實的修復點

- **計畫語意錯誤回饋太晚。** 第 12 次證明：只在 session 結束後驗證，模型沒機會根據核心錯誤修正。現在 `validatePlan` 共用真實 transition 規則做唯讀預檢，缺少的驗收 ID 明列；無效 case_result 不關閉 session。正式 dispatch 仍重驗版本、授權及來源，不把預檢當提交。
- **自然語言收尾被當成無法恢復。** 第 13 次只回文字便停止；現在原 session 在剩餘回合／時間內最多補問一次，要求交回結構化結果。第 14 次 planner 實際用到這次補正，才成功提交完整計畫。回歸涵蓋再次失敗不無限問、回合用完、取消與已接受回報後不再操作。
- **拒寫缺少可行資訊。** 新錯誤明列要求路徑及允許範圍，觀察保存 writeRequest 而不保存內容；仍拒絕同一越權路徑。這修復診斷／操作資訊，不代表第 10 次的未知路徑已查明。

獨立程式審閱未發現這些修正擴權或繞過驗收。第 14 次仍有多餘讀取，曾改用絕對路徑被拒後自行回到相對路徑；沒有取消路徑保護。整合者文字另誤稱只用 1 attempt，權威狀態實際保留 3 次 worker attempts；預算依核心計數，不採模型自述。不得因整案 pass 就把所有模型敘述當真。

### 根因界線與目標復盤

**已定位的是多個框架接線／錯誤恢復缺陷，不是證明「pi 壞掉造成全部失敗」。** 清潔 pi 原生工具能完成工作；獨立工作包也可成功。[recurrent／MTP 查核](../research/2026-09-06-recurrent-cache-triage.md)發現相關上游問題但本機已有多項修正，不能直接歸因。關閉快取尚未完成可比較的整案實驗，因此不修改使用者模型服務、MTP 或全域設定。

第 14–15 次證明目前修正已能走完整條回饋流程，並非只會安全停止。但這個刻意設計的簡單案例每次用了七個 session、約八分鐘；不把它說成日常小工作的最佳路線，也尚未證明長 context、跨模型或降低成本。依事先說明，只執行一次同版確認，成功後不繼續消耗模型；沒有增加角色、放寬授權／驗收或重試到成功才保留結果。整體目標仍是本地模型正確交付且降低使用者負擔。

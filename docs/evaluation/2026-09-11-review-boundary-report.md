## 可重現根因與修正

核對者實際傳回 `{"result":{"passed":true,"findings":[...],"evidence":"..."}}`，不是 runner 要求的頂層 passed／findings／evidence。原 SDK 僅為 planner／worker 提供角色格式驗證；reviewer 的合法 JSON 被當作合法回覆，runner 取出不存在的欄位，狀態層遇到 undefined 才報 `INVALID_ARGUMENT: Value must be plain JSON`。

修正 reviewer 的 SDK 工具／最後文字及自訂 session 回傳邊界：拒絕包錯層、缺欄位與不合規資料，提示正確形狀，使用既有同 session 格式修正額度。保留原始拒收回覆、否決結論與結構化證據；不自動拆包、不改成果、不改預算、不把格式正確當成語意正確。

三個回歸反例先失敗（錯誤回覆未被拒收），修正後通過；另檢查否決與空證據等邊界。既有三個 SDK 測試只回傳 passed 的不完整替身已改為完整核對形狀。完整 kit **311 通過、2 項 Windows 符號連結權限跳過**。獨立審閱未發現阻擋問題，針對性 62 項通過；指出工具反例直接呼叫 execute，不涵蓋真實 pi schema 層的修正行為。因此尚未以本機模型驗證修正後的正常整案。

## 不可被格式修復掩蓋的品質問題

核對者零次讀取卻宣稱逐欄核對，說明中的 bins、piSkills、installerRelated 等與真正成果不符；例如把 installerRelated 說成 CHANGELOG／HOSTS／README／SOURCE。沒有接受它的 passed 作為成功證據，更不能自動拆包後宣稱驗收完成。

另觀察 planner 與 worker 在已接受 case_result 後仍各進行約 32.484／37.745 秒壓縮。這是保存的事件順序與耗時，不是本輪已修正項；其 SDK 結束生命週期需獨立重現，不能直接關閉所有壓縮。

## 復盤與接續決策

原案的獨立 context 是為了可信核對，不是讓另一個角色說「通過」即可。下一步優先處理**核對結論如何連到本 session 實際取得的成果與來源證據**，以保存的零讀取反例驗證；讀取回條最多證明取得材料，仍不能保證理解。另定位已提交結果後的壓縮成本，不再原樣從頭抽樣到成功。

本次只修已重現的格式交接缺口，不為上述未解問題補寫成功。工程修復、正常模型失敗與未驗證效果分列；保留工作分支，不合併／推送。模型服務、全域 pi、AppData、備份均未修改。公開 JSON 只比本機原檔多最後換行；舊失敗與成本不覆寫。

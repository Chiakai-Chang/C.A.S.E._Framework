# 分層回饋：實作與本機探測記錄

日期：2026-09-06。依[確認的方向](../research/2026-09-05-layered-cooperation-direction.md)與[實作計畫](../design/2026-09-05-feedback-implementation.md)，目標仍是讓本地模型把工作做好，降低人的監督與重述負擔，不是增加角色或記錄量。

## 本輪實際新增

- 專案共識在既有 manifest 保存版本與來源引用，新卷宗繼承快照；來源／共識改變時需明示對齊，不另建通泛的根目錄檔案。
- 保持契約不變的計畫修正、缺口補包與全域失敗後補做；保留未受影響的有效成果、歷史失敗與累計預算。未知副作用不自動接管。
- 必要大型材料可索引取用，限制仍直接進 context；現有工具的讀取上限不變，不宣稱可無限處理資料。
- 人類確認的可執行檢查，保存真實 exit code／輸出，模型不能覆蓋失敗。命令及其執行的程式仍具有使用者權限，不是 OS sandbox。
- pi 的 `case_result` 結構化回報與實際能力紀錄，區分文字驗收項目、核准命令 ID、可用工具與寫入範圍。

操作見 [V2](../../workflow-kit/docs/V2.md)。其他 AI 工具共用技能與核心，不等於已有跨產品自動派工。此輪沒有改全域 pi、啟動新模型服務、建立排程或使用雲端模型 fallback。

## 行為與指引驗證

本機 Windows／Node 24.19.0：`npm test --prefix workflow-kit` **110/110 通過**。真實檔案／狀態測試涵蓋補前置、外部缺料、成果保留、失效傳播、權限與預算、不合法重規劃不能洗掉整合 false、可信檢查失敗、結構化回覆後禁止繼續操作，以及來源版本變更。模型／SDK 外部邊界使用替身，不把這些測試當作模型品質證據。

獨立程式審閱與新增傳輸／能力資訊的增量審閱未發現可確認的阻擋缺陷。原生 pi 0.84.2 的實際 loader 以記憶體設定載入目前套件，`case_workflow` 與 `/case` 註冊成功、errors 為空；這一項沒有呼叫模型，不冒充再次完整安裝／移除實測。dry-run 封裝含 32 個檔案，包括新增核心及 pi 模組，不含模型、測試資料或私有快取。

技能參照試讀：舊指引無法回答「新增可補前置、跨卷宗共識、授權 node --test」；更新後另一個 context 能找到對應回覆、核心動作與人類命令。試讀又發現 `project:` 前綴可能重複加上，已明示由核心產生並再次核對。這是有限的參照可用性檢查，不是跨模型遵循率。技能結構驗證通過；Windows Python 預設 cp950 無法讀 UTF-8 檔案，改用 `-X utf8`，未改動全域編碼或原始文件。

## 本機模型探測：失敗也保留

資料與機器設定：沿用已在運作的本機 llama.cpp／Qwen 模型，SDK 設定 contextWindow 32768、maxTokens 4096、thinking off、每 session 設定最多 12 個模型回合（不是 12 次工具呼叫）。模型識別、程式雜湊、來源雜湊、實際回報／工具觀察與失敗見[完整記錄](case-feedback-development-evidence.json)。只存最終回報和工具觀察，不要求模型提供隱藏推理。

主案例是四份合成來源：訂單、價格、退貨、匯率。先產生逐筆正規化，再產生總表，手算結果為 USD 20、EUR 16、TWD 1200。刻意由測試準備一個缺少正規化前置包的計畫，檢查 worker 能否回報，planner 補包並續作。因此這不是自主規劃基準或未參與開發的 holdout。

| 探測 | 結果與實際時間 | 觀察／處理 |
|---|---|---|
| 1：原始純文字回報 | 失敗，43.959 秒 | worker 正確提出 changeRequest，卻因前置說明文字被嚴格 JSON 解析拒絕；沒有產物 |
| 2：窄範圍 worker 回饋處理後 | 失敗，110.106 秒 | worker 進入 planner，但 planner 的合理計畫也因前置散文被拒絕；沒有把此結果當成功 |
| 3：結構化回報後 | 失敗，301.221 秒 | worker／planner 使用 case_result；下一 worker 誤稱缺寫入工具、把文字檢查 ID 當核准命令，最後耗盡五分鐘預算 |
| 4：明示實際工具與檢查 ID | 失敗，481.223 秒 | 送出前 payload 含 case_write，但執行者反覆讀取／列出資料，32 次工具呼叫、沒有寫入，最後耗盡八分鐘預算；沒有產物 |

第 3 次後以相同原生 SDK、隔離設定建立 worker，在模型呼叫前停止：allowed、active、registered、model-visible 四份工具清單都有 case_write，模型呼叫數為 0。沒有重現工具漏接，支持能力誤認這個判斷；第 3 次沒有保存供應端請求，不能宣稱已證明當次端點收到的內容。第 4 次才另加正式 payload 建立後、HTTP 送出前的工具名稱紀錄，不保存密鑰或完整請求。

第 4 次共 19 次送出前 payload 觀察，三個 session 分別為 5、4、10 次；最後 worker 的 32 次工具呼叫可發生在同一模型回合內，不能據此認定超過 12 回合限制。既有 SDK 原始碼每個模型回合發出 turn_start；本次由整案時間預算先中止。累計 SDK total tokens 為 88,562（包含快取），獨立產物檢查未通過，沒有產物。這不支持「只要明示工具就能解決」的假設。

前 3 次保存核心及整合程式雜湊；第 4 次另保存探測程式自身雜湊。不同開發版本及時間預算不能混成成功率、配對統計或因果改善結果。SDK token 數是累計用量，不是峰值 context；峰值 token、硬體／電力成本未量測，均屬未知。

## 復盤：哪些決策真的幫助目標？

1. **結構化回報取代純文字格式依賴。** 問題不只是模型不遵守一句指令；內容合理仍可能在交接失敗。正式資料由工具傳送，敘述另存原文，核心繼續驗證，代價是多一次工具互動與可能的模型 turn。
2. **能力資訊從實際工具產生。** packet 的 checks 是驗收描述，不是可執行命令；把兩者混在同一名稱之下容易誤用。增加少量、可核對的能力資訊，不增加權限。是否提高可靠度仍由實測決定。
3. **計畫修正不等於改標準。** 局部失敗可補做，但不能重設預算、擴權、重播未知副作用或用第二個「通過」掩蓋第一個整合失敗。這些由程式驗證，不依靠道德式提示詞。
4. **測試入口保留相容性。** 沿用明列測試檔，避開已有證據的 Windows／Node 20 萬用字元問題；代價是新增測試時需同步清單。不再為此新增一個測試框架。

## 尚未證明／尚未交付的部分

此輪不是原始構想全部完成的宣告。三條件公平比較（原生／技能／完整流程）、不同本機模型、長 context 壓力、跨產品真實交接，以及可選取的跨任務經驗索引／重用，仍未驗收。不能以本輪機制、程式測試或單次產物正確宣稱已提升一般任務品質。

下一步先縮小執行介面的選擇負擔：以同一個正規化工作比較現有工具迴圈與「模型只提交候選產物、程式核對並受限寫入」的模式，保留一般工作需要的工具路徑，不把特定資料案例寫死成通用框架。先看產物正確率、讀取重複與總成本，再決定是否納入；不繼續無限制加提示詞，也不以增加角色代替可靠執行。這是待驗證的方向，不是已實作能力。

目前保留預覽分支，尚未合併／推送這輪變更；公開授權也仍未選定。原始構想與一手來源繼續由 MAP 按需導航，未因這次實作被改寫成效果結論。後續判斷先看真實成果、額外成本與人的介入，沒有收益的階段可刪減，而不是繼續增加流程。

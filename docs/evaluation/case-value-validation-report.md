# 固定版實際價值驗收

日期：2026-09-06。依[事前設計](2026-09-06-value-validation-plan.md)完成六次本地模型執行，沒有人工補答案、失敗重抽或途中修改核心。**本輪沒有觀察到完整 CASE 分工的品質優勢；直接執行／摘要接續較快。** 不代表所有長工作都無效，也不能把機制可運作說成效益已證明。

## 結果

| 情境 | pi 簡單流程 | CASE 完整流程 | 本輪判讀 |
|---|---|---|---|
| 簡單資料轉換 | 通過；24.751 秒；11446 tokens；1 session | 通過；129.893 秒；36390 tokens；4 sessions | 成果同樣正確，完整流程約慢 5.25 倍，不推薦用於此類工作 |
| 多來源、多項規則 | 通過；60.774 秒；18931 tokens；1 session | 失敗；199.222 秒；51099 tokens；4 sessions | 前段正確，後段自稱寫好卻沒寫檔；多檔案不構成分工優勢 |
| 實際前段成果後換 context | 通過；110.432 秒；39907 tokens；2 sessions | 通過；323.674 秒；94279 tokens；5 sessions | 都能保留前段並接續，CASE 約慢 2.93 倍；未見超越良好摘要交接的品質收益 |

表中 tokens 是 SDK 累計，包含 cache read，**不是單次 context 大小或實際運算量**。耗時包含當次設定、記錄與核對；未隔離背景系統負載，不是精密速度 benchmark。三類不同工作各一對，3/3、2/3 只描述本次六筆結果，不能估計普遍成功率。所有來源內容均未改。

基準同樣使用 pi SDK 的模型工具迴圈與 CASE 限定工具／回報傳輸，省略 CASE 的規劃、獨立核對及整合，不是原生 pi 預設工具體驗。接續案基準使用兩個新 session，保留原需求與第一階段真實摘要，不是讓它失去必要資訊。兩邊都由模型實際生成 normalized；CASE 的兩包接續計畫由操作者事先指定，不是自主規劃測試。CASE 多來源案則由模型自行規劃。

## 失敗的具體位置

多來源 CASE 前段 normalized 正確處理了現行價格、取消訂單、只扣已核准退貨、保留零數量列及原幣／換匯計算。後段 worker **只呼叫一次 case_result，沒有任何 case_write**，卻回覆已寫 report.json。核心正式提交時因檔案不存在回報 `MISSING_INPUT`，沒有錯誤結案；外部評分也判失敗。

這不是模型能力全然不足：同模型的簡單流程正確交付兩檔；也不是證明快取或 pi 安裝損壞。可定位的產品缺口是：worker 回報被接收、session 結束後，才發現缺產物，沒在原 context 提供修正機會。先前 planner 預檢修正尚未涵蓋這種 worker 完成回報。本輪不修改凍結版本，不將修正後重跑混入結果；這項待修應以實際寫檔為驗收，不能用多問幾次「完成了嗎」替代。

## 設計裁定與使用方式

1. **直接完成是第一選擇。** 不能因檔案多、任務有步驟或框架存在，就自動拆成多個角色。
2. **需要接續時，先用原需求＋實際進度／產物的交接摘要。** CASE 的持久化版本、相依與來源檢查仍是可選管理能力；本輪沒證明它比摘要接續更準或更便宜。
3. **完整 pi 自動分工維持明確選用的預覽。** 適用於需要保留工作包版本、獨立核對紀錄與回饋責任的使用者；這是功能需求的選擇，不是已證明提升模型品質的推薦。
4. **不再擴充角色／平台或調參掩蓋差距。** 保留已有完整功能，不重做；公開說明先對齊以上結論。要繼續修復，先處理「模型宣稱寫入但沒產物」這個具體恢復缺口，不先增加新架構。

原始構想的目標沒有改：讓本地模型在有限 context 下把工作做好並降低使用者負擔。這次發現的是「完整分工不能被當成達標手段的預設答案」，不是把目標偷偷降為多寫紀錄。長 context、真實軟體開發、跨模型、獨立核對的消融比較與日常人工負擔仍未測；**本輪驗收完成，不等於整個原始目標已全部達成。**

## 重現與證據

執行入口（只呼叫既有 localhost 模型，不修改全域 pi 或模型服務）：

```text
node workflow-kit/evaluation/value-comparison.mjs --sdk <pi的dist/index.js絕對路徑> --output <新的JSON檔案>
```

固定六次順序為 simple single/case、multi-source case/single、resume single/case；每案整體上限十分鐘、每 session 十二回合、medium、宣告 context 32768、輸出上限 4096。實際 payload 的思考開關與採樣欄位另存；沿用服務預設而未提供 seed 的欄位不補猜。服務自報 build `b11500-776183047`，實際模型是本機 Orcarouter STRIX_LEAN。沒有呼叫雲端模型。

[公開證據投影](case-value-validation-evidence.json)保存設定、程式／來源雜湊、成果、評分、原始最終回報、工具順序／錯誤、用量、接續狀態及原檔 SHA256；不是完整 trace 的逐字副本。完整原始紀錄在本機 `.npm-cache/value-comparison-20260906-01.json`，六個獨立暫存專案及產物保留。未收集隱藏推理。

工程驗證 125/125 通過，新增六個測試保護評分與失敗保存，並已同步 package test 清單。獨立執行前審閱發現的初始化漏記、目錄型錯誤產物與需求歧義均在第一次模型執行前修正；這些是評估工具驗證，不是模型效益證據。產品核心未因這輪比較改動，既有修復尚未合併／推送。

收尾再次從六個專案重評產物、重算來源雜湊，與公開投影一致；完整原檔 SHA256 及凍結程式雜湊吻合，所有實際 payload 都啟用思考且輸出上限 4096。11 份相關文件的 144 個本地連結無缺失。獨立結果審閱未發現數字錯誤或小樣本效果誇大。這些檢查確認紀錄可信，不使失敗案例變成通過。

# 修復執行設定：思考開關固定對照

日期：2026-09-09。產品基準 `6b44bf1`。使用者同意：沿用已保存的修復交辦，只比較執行設定，不重跑規劃與首次核對。

## 要回答的問題

[前批](2026-09-09-review-repair-report.md) reviewer 已自行找出缺欄並退回，worker 卻在約 260 秒內遇到回覆上限、沒有寫入。不能再以「缺少核對」解釋所有失敗。本批測試在相同材料、缺欄成果、明確核對回饋及相同時間額度下，思考開啟與關閉是否影響實際修復。

## 事前條件

- 共用前批 worker 的原始 prompt，包含該 reviewer 自行提出的修復意見；兩組同樣取得，不是從評分器餵答案。原始缺欄成果核對寫入雜湊後複製到兩個新隔離目錄。
- 固定順序 off → medium，各一個新 session、最多 600 秒／16 turns，context 宣告 32768、回覆上限 4096。這是新診斷額度，不拿前批只剩 260 秒的 worker 當本批基準。
- 相同 SDK／模型／工具／來源／回報驗證；只改 SDK thinkingLevel。實際 request 檢查 enable_thinking 為 false／true；preserve_thinking 由既有相容設定保留。medium 並不等於伺服器收到中等推理 token 額度。
- 本批使用相同 worker 專用工具集合，未加入獨立 reviewer、integrator 或可執行檢查；回報前檢查檔案存在與來源未變，正確性由結束後的隔離 oracle 判定。沒有人工追加提示或樣本替換。
- 開始前固定診斷程式、pi/core、評分模組、前批證據與 SDK 入口雜湊；開始及每組前核對來源／成果、模型／服務預設，每組後核對程式。未凍結 GGUF 與 SDK 全部相依，不稱完全重現環境。

`workflow-kit/evaluation/repair-thinking-pair.mjs` 是開發診斷，不改產品或全域預設，不隨套件發布。固定順序、未固定 seed／重置 cache、不同隔離目錄（名稱亦不同）均限制因果推論；不宣稱盲測或成功率估計。新組做完不提前取消基準；兩組若有來源變動、額外檔案或沒有可核對請求才停止。

## 裁定與實際採用

1. **這次修復不是模型做不到**：兩組都補齊正確欄位，且沒有降低驗收或人工救援。既有寫入工具與這份修復交辦足以完成指定工作。
2. **更長思考不是本案的免費品質提升**：本次 off 較快且產物同樣正確，但固定順序、隨機性及快取限制，不將約 3.48 倍耗時差外推成穩定加速率。這也不證明思考設定是所有歷史失敗的唯一根因。
3. **以前的逾時應重新判讀**：前批 worker 剩約 260 秒，本次 medium 花約 458 秒才能完成；這與「核對消耗預算後修復時間不足」一致，但不是同一隨機軌跡的反事實證明。不能刪去先前 length／逾時失敗。
4. **先採用現有設定，不新增框架功能**：對本機這類已定位、範圍明確的修復，off 作為後續驗證的優先候選；不全域關閉所有角色思考，也不修改使用者 BAT。`sdk-session.mjs` 既有預設就是 off，pi extension 沿用 `ctx.thinkingLevel`（缺省 off）；之前比較程式是明確指定 medium，不是產品強制要求。
5. **下一個交付門檻**：在相同配置候選下驗證修復後的獨立核對與 integration，再確認完整使用旅程；本批 oracle 雖完整通過，仍不是完整框架流程已通過。之後才依總成本評估提早結構檢查／減少重讀，不為這次結果添加新角色或大型檢查系統。

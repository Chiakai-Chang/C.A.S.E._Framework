# 實際價值驗收：固定版小型比較

目標：判斷 CASE 的分階段與接續成本是否換來更正確、保留限制的成果，不再以框架測試數當效益。接續 [GOALS](../GOALS.md) 與[核心修復](case-core-repair-report.md)。本輪不改產品流程、模型服務或全域 pi。

## 事先固定的設計

- 三種工作：簡單資料轉換、多來源及多項限制的彙整、完成第一階段後換 context 接續。各一對，六個獨立暫存專案；按情境交替先執行單 session 或 CASE，不失敗重抽。
- 兩邊使用同一 pi SDK、同一本地模型、medium、32768 context、4096 輸出上限、同等讀寫工具／材料／整案 600000 ms；每 session 12 回合。CASE 多 session 的額外消耗照算，不給時間加成。比較開始後核心程式不修改，逐案驗證雜湊。
- 單 session 基準沿用 pi 的模型工具迴圈與相同限定工具，沒有規劃／審查／整合角色。這是控制工具差異的比較，**不是未修改的 pi 預設體驗**；不能把差異全部外推成一般 pi 的效果。結果需清楚使用此名稱。
- 接續情境的第一階段由兩邊各自的模型實際完成，不灌入正確成果。待第一次成果保存後結束原 session，再新建 context；CASE 使用已有卷宗，基準取得原始需求與上一階段實際回報。第一階段的時間與 tokens 計入。這是安全階段切換，不是殺程序／未知副作用恢復。
- 接續案兩邊都預先指定「先 normalized、後 report」階段。CASE 由操作者建立這兩包計畫，不計不存在的 planner 呼叫；只比較接續，不據此宣稱自主規劃能力。其他 CASE 情境由真實 planner 規劃。
- 檢查直接從不可變來源計算預期 JSON，比對完整欄位與來源雜湊；不執行模型產生的程式。兩邊同樣無任意 shell。模型自行核對，外部評分另算，不將模型自稱成功當通過。

## 結果與判斷

各案保存：模型／程式／來源雜湊、實際送出設定、所有 session 最終回報／工具觀察、階段切換、成果、錯誤、耗時與 SDK 用量。累計 tokens 含快取不是峰值 context；用量缺失不可填零。人工介入僅記本輪是否修正或提示，不以無人介入的合成案例宣稱已證明日常省心。

成果正確、限制保留、流程完成分開評分。兩邊都對且 CASE 更慢時，該案不推薦完整分工；CASE 正確而基準失敗時，只列為該情境的正面訊號，不能以單對推廣成功率。兩邊都失敗則無效益證據，不當場調參到成功。接續只判斷能否從真實前階段產物接回，不宣稱長 context 品質提升。

完整六次結束即停止生成，依結果更新使用建議、STATUS、READINESS 與英文說明。若尚無優勢，明確說尚未證明，保留輕量記錄／接續價值，不追加架構掩飾。跨模型、長 context 壓力與原生 pi 預設體驗是本輪未測邊界，不是完成這輪的新增前置條件。

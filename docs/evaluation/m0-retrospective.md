# M0 復盤與接手摘要

日期：2026-09-05。目標是降低人的認知、抉擇與重建脈絡成本，同時提高可驗證品質。M0 選取了最小的卷宗完整性實驗；完成這個里程碑不等於整個框架可用了。

## 有價值的成果

工作狀態有明確版本與摘要，交接和驗收綁定具體內容；衝突、過期證據與恢復都有可檢查的語義。140 個受控規範案例和反向測試把規則變成可執行檢查。原始評估結果連同失敗、改判理由一起保留，讓接手者能區分觀察與推論。

## 這一輪暴露的問題

平台保證的門檻使目前 Windows CLI 無法初始化，因此最關鍵的真實使用旅程仍缺證據。r6 的 Markdown＋Git 基線四案皆成功偵測，不能沿用已撤回的 r3 結果聲稱框架較好。先前活文件曾殘留這個舊結論，已經獨立審閱修正。

大量審閱與評估器強化提高了證據可追溯性，也累積了流程和維護負擔。測試全綠、更多角色或更多審閱輪數，都不能代替使用者能完成任務的證據。只改說明文件後反覆執行約九分鐘的完整測試，收益也有限；今後依實際變更風險選擇驗證，只有程式、規範或未解疑慮變動才擴大重跑。

原 README 以全域安裝開場、缺乏文件地圖，容易讓讀者誤解成熟度。此次整理補上可用性表、按需閱讀入口與本機查看說明的路徑，保留原有技術與历史資料的位置以免破壞引用。

## 收斂決定

合併至主資料夾後另發現可重現的取出問題：Windows `core.autocrlf=true` 會把 34 份原始評估 JSON 轉為 CRLF，與已凍結的 LF 摘要不符。以 `.gitattributes` 的 `-text` 規則保存結果原始位元組，並加入啟用 autocrlf 的獨立 Git 取出回歸測試；原始 Git blobs 與完整性清單不改寫。這說明接手環境驗證可以找到原工作樹重跑測試未揭露的問題。

維持 **narrow**：先證明一個真實 filesystem adapter，再做新的配對評估，之後才投入 skills、plugins 或多宿主協作。命名空間仍是 `.case-agent/`；框架本身的 README、MAP、CONTRIBUTING 不會由 init 寫入採用者專案。

跨平台有兩個獨立問題：作業系統的檔案能力，以及 Codex／Claude Code／Pi 的宿主整合。共用檔案協定提供基礎，兩者仍需分別測試。授權與公開套件發布亦尚未決定。

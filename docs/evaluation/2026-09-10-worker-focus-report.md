日期：2026-09-10。目標仍是讓本地模型把工作做好，而非增加流程或研究量。本次接續[壓縮修復後仍未產出](2026-09-10-search-and-role-report.md)的問題，先區分模型基本工具能力、附加資料量及完整任務負荷，再調整交辦呈現；不改驗收標準。

最後一次第一次提交即通過，**未觀察到拒收後修復**。不能宣稱語意檢查造成改善，也不能把 8 回合失敗與 16 回合成功當成等預算比較。語意檢查只用於該診斷，未加入後續正常完整流程；評分答案沒有交給模型。

可成立的觀察：本機模型不是完全無法寫檔；附加全文不必然讓簡單工作停滯；同一完整成果在較精簡的單一執行 context 中可以完成。尚不能成立的結論：交辦冗長是唯一根因、索引一定提高品質、完整 CASE 已通過，或任何模型／任務都有相同效果。

## 有界修改

pi 執行者交辦改為：未指定 delivery 的來源預設保留版本化索引，按需讀取；明確 inline 仍附全文，明確 indexed 保持索引。可攜核心及 CLI 的既有預設不變。限制、目的、驗收、必讀責任、來源版本與過期拒絕均保留，不重寫卷宗狀態。這呼應[原始分層協作](../research/2026-09-05-layered-cooperation-direction.md)：交辦足夠材料，而非每層重複所有材料。

先以核心與實際 runner 邊界反例確認舊行為失敗，再實作。完整工程測試 306 項：304 通過、2 項 Windows 符號連結權限跳過。獨立程式審閱未發現阻擋問題；審閱者沒有代跑模型，不作模型效果證據。

## 證據限制與接續

四次診斷專案位於 repository 下，會繼承其適用指引；policy trace 已保留。這與正常完整流程的獨立暫存專案不同，不隱藏此混淆因素。原始檔保存提示、模型設定、工具呼叫與輸出、產物、雜湊、失敗與用量；公開副本僅附加檔尾換行。SDK 全相依樹及 GGUF 位元組未凍結；SDK 入口雜湊不能替代全樹。累計 tokens 不是峰值 context，未回報成本不算零。

後續正常完整流程使用獨立固定 manifest，沿用原任務、來源、600 秒、16 回合／session、5 次嘗試；沒有測試評分器回饋或合成否決。單獨執行的成功不得拼接成該完整流程成功。

相較先前無產物，這次進展是**完整流程內已有正確成果**；不是「索引必然造成成功」的因果證明，更不是完整驗收成功。當前關鍵由完全未產出，轉為規劃重複解題及剩餘驗收時間不足。後續應優先讓交辦保持精簡、欄位回饋可修正，並驗證從正確成果到獨立驗收的接續；不再原樣重跑、加模型預算或新增角色。若獨立測接續，必須另記新增成本，不能改寫這次 600 秒未通過的結果。

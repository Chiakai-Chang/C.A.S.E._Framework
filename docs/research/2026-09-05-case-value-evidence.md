# C.A.S.E. 的價值與技能遵循：證據界線

日期：2026-09-05。研究筆記，可依新證據修正；不是產品成效證明，也不變更目前操作規格。

## 問題與判斷

使用者觀察：不同本地模型讀取同一份技能，反應與遵循程度不同。這是需要分解的實務問題，不表示原始構思沒有價值，也不能直接歸因於模型太弱。

研究支持「取得指引、依規則操作、正確完成工作」是不同問題；尚未證明 C.A.S.E. 能解決它們。本框架值得驗證的假說是：用全局目標、範圍清楚的工作包、必要的程式檢查、獨立驗收及接續資料，減少遺漏與人工重述，同時避免流程成本超過收益。

## 查核的一手研究

### SWE-Skills-Bench（2026-03，初步預印本）

以 Claude Code／Haiku 4.5 評估 49 個技能、565 個工作，平均改善約 1.2 個百分點。不能據此宣稱所有技能無效：多項基線已滿分，且不是本地量化模型或長期協作測試。文內技能放置位置的說明也有不一致，重現前須核對程式。[原文：方法與結果](https://arxiv.org/html/2603.15401v1)

### SLBench（2026-07）

86 個刻意挑選的挑戰案例，指出模型可能完成主要動作卻漏掉前置條件、限制或後續義務。SLGuard 的改善是在單一組態、11 個原失敗案例測得，且將部分無違規但未明確成功者合併計為安全；不是實務失敗率或普遍成功保證。[原文：§4.3、Limitations](https://arxiv.org/html/2607.09016v1)

### Skill Following（2026-09）

比較同一工作有／無技能，並區分實際取用技能的子集，提醒「讀過」不等於「有幫助」。其 RAE 是特定協定下的成對訊號，不是無偏因果估計或模型總能力分數；單次程式與數學測試不能外推長期協作。[原文：Limitations](https://arxiv.org/html/2609.00549v1)

## 對本專案的設計推論（待實測）

- 技能負責解釋目的、方法與例外；範本負責交辦完整性。不要把自然語言規則說成強制保障。
- 可機械判定的條件交給程式，例如依賴是否完成、產物版本是否與檢查結果相符。若 agent 可以繞過工具直接改資料，就不是不可繞過的保護。
- 獨立驗收看原始目標與實際產物，不只看執行者摘要；獨立對話仍可能共享同一模型偏誤，不能當成絕對正確。
- 模型能力不足時，縮小工作包、減少同時生效規則、回報具體不合格項目；不靠無限制重試。全局推理不足不能只用更多範本補救。
- 保留原本全局規劃與整體驗收：所有子任務通過，仍可能沒有完成使用者真正的要求。
- 先辨識是沒載入、沒理解、漏執行、工具格式錯誤、context 遺失、產物錯誤或驗收漏判，再決定改提示詞、工具還是模型設定。

以上是架構假說，不是上述論文替 C.A.S.E. 背書；三篇也未驗證使用者目前的本地量化模型、伺服器與 pi 組合。

## 如何公平驗證，而不再用測試數代替價值

同一批需求、初始檔案與驗收條件，配對比較：

| 條件 | 配置 | 要回答的問題 |
|---|---|---|
| A | 一般清楚指令與現有 AI 工具 | 不用 CASE 時的基準 |
| B | A 加技能與範本 | 文件本身帶來什麼增益與成本 |
| C | B 加實際狀態檢查、證據取得、獨立驗收 | 可執行流程是否比純指引可靠 |

事先固定模型／量化、推論設定、AI 工具版本、context 上限及總預算；每組重複執行並保留失敗、逾時與未定結果。既要比較相同總預算，也要另列 C 使用較多資源換來多少改善，不能只給 C 額外模型成本卻宣稱架構勝出。

案例包含一般短工作、限制很多的工作、跨對話接續、前置缺口，以及子任務全過但全案漏需求。驗收者不看實驗組別；可執行條件直接測產物，語意條件用事先寫定的評分規則與必要人工抽查。不得讓實作者看隱藏答案或修改評分規則。

主要比較成果正確、違反限制、誤結案、接續遺漏、人工介入次數、時間及總 token；同時記錄技能是否實際載入與依規則操作。若短工作沒有收益，允許不啟用完整流程。若 C 改善但成本過高，移除無效環節，不繼續增加角色或文件。

本輪只有來源查核，尚未執行上述 A／B／C 實驗。使用者實測不是交付前置條件；實驗應由開發者在隔離環境辦理。

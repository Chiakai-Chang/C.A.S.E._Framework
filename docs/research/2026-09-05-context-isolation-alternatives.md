# Context 分離是否也能幫助強模型？既有研究與替代方法

查核日期：2026-09-05。這是來源研究與設計推論，不是 C.A.S.E. 的效果實驗。主要目的仍是讓本地模型把工作做好；保存研究是為了可追溯與滾動修正。

## 本次問題與結論

使用者提出：即使能力較強的模型仍有 context 上限，規劃／執行分離、大憲法對應小憲法是否仍有幫助？是否已有類似研究或更好的方法？

有相關研究與實務，而且問題不只存在於小模型。需要分清「單次能容納多少資料」、「能否可靠運用其中的資訊」與「跨多次執行能否保留正確狀態」。目前證據支持按任務管理必要脈絡的方向，不支持所有任務都拆成多代理、context 越短越好，或 C.A.S.E. 已優於其他方法。

## 原始來源與限制

### 1. 長 context 的容量不等於資訊利用品質

[Lost in the Middle，arXiv:2307.03172v3](https://arxiv.org/abs/2307.03172v3)，2023-11-20 修訂；本次核對摘要與版本資訊。多文件問答及 key-value retrieval 的結果受相關資訊位置影響，部分受測模型在中間位置表現較差。這是設計測試的理由，不是當前模型必定呈現相同退化曲線的證明；更不能據此填入目前助手的未測效能數字。

### 2. 強模型也需要跨 context 的工作接續

[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)，Anthropic，2025-11-26；核對問題、初始化、增量工作與測試段落。作者描述 Opus 4.5 即使使用具壓縮功能的 SDK，仍可能留下難以接續的半成品或過早認定完成。其工程做法分成初始化與後續工作階段，利用進度、Git、功能條件和端到端測試維持接續。這與 CASE 有直接相似處，但屬特定產品開發情境的第一方經驗，不是本地模型對照實驗。

### 3. 多代理的收益，可能同時來自花費更多資源

[How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)，Anthropic，2025-06-13；核對 benefits 與 architecture 段落。其研究系統由主代理委派獨立搜尋，適合多個可分開探索的方向；也提醒共享脈絡及相依關係密集的工作不一定適合。文中多代理約 15 倍 token 的比較對象是一般聊天，不是所有單代理系統。內部品質結果不能解讀成相同總預算下，僅靠 context 隔離就得到等量提升。

### 4. 架構必須配合任務，不能直接套通用倍率

[Towards a Science of Scaling Agent Systems，arXiv:2512.08296v3](https://arxiv.org/html/2512.08296v3)，2026-04-08；本次先讀 v1，後核對 v3 摘要、穩健性與限制，結論以 v3 為準。研究擴展至 260 種設定，報告可平行任務與嚴格循序任務的收益方向不同；後者可能因協調而退步。

限制：受測設定不是 CASE、目前助手或使用者的量化本地模型。作者指出架構／模型專用提示未最佳化；新增 SWE-bench Verified 與 Terminal-Bench 各僅 20 個實例，個別比較信賴區間寬。不同模型的部分架構結果也不一致。因此不把文中 45% 門檻、錯誤倍率或架構預測率轉成 CASE 的通用規則；目前採用「需要配對比較、相依關係與協調成本很重要」的保守結論，未重現其實驗。

### 5. 隔離、檢索、筆記與壓縮是互補工具

[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)，Anthropic，2025-09-29；核對全文。文中將按需取資料、結構化筆記、壓縮及子代理列為不同工具；重點是足夠且高訊號的資訊，而非單純最短。過度摘要可能丟失細節。這支持 CASE 保留來源位置與回查能力，不要求執行者只能相信規劃者的摘要。

[OpenAI Compaction 官方文件](https://developers.openai.com/api/docs/guides/compaction)，本次由主代理核對官方頁面。壓縮以較少 token 保留關鍵狀態，結果可包含非人可讀的 opaque 項目；送入壓縮的內容仍須符合模型輸入限制。這是特定 API 的接續能力，不等於無限單次 context，也不取代可攜、可查核的專案工作記錄。

### 6. 替代方向：把長資料留在外部，由程式按需處理

[Recursive Language Models，arXiv:2512.24601v2](https://arxiv.org/html/2512.24601v2)，2026-01-28；核對摘要，限制段落由主代理補充核對。RLM 把長輸入放在外部環境，讓模型透過程式查看、分解及對子片段呼叫模型，而非將全文一次放入 context。這與 CASE 工作包不同，但可成為大量材料的取用方法。

限制：其四種長 context 任務不等於通用專案開發；Qwen3-8B 的部分結果涉及後訓練，不能宣稱只改提示就有同樣收益。論文亦討論同步呼叫、受測遞迴深度與延遲限制。CASE 不應因此立即新增完整 REPL／訓練框架；先採用可回查來源及有界取用即可。

## 對 CASE 的設計判斷（待驗證）

這裡是根據來源形成的工程建議，不是上述作者對 CASE 的背書。

| 工作情境 | 優先做法 | 避免的代價 |
|---|---|---|
| 小而完整、依序推進的工作 | 同一執行 context，必要時查檔 | 為分工而分工、重複交代 |
| 規劃探索產生很多無關材料 | 規劃後交付工作包，在新 context 執行 | 把全部試錯歷史塞給執行者 |
| 長時間、多階段工作 | 外部狀態、可回查證據、階段接續 | 只依賴有損聊天摘要 |
| 多個真正獨立的調查／工作 | 分開 context，回傳有來源的結果再整合 | 全部代理共享相同巨大歷史 |
| 相依密集或跨模組修改 | 保留共同限制與介面，集中整合 | 局部皆通過但全域失敗 |
| 大量文件或資料 | 搜尋／程式切片／按需讀取 | 將外部資料總量誤當單次 context 必須承受的量 |

大小憲法仍有價值，但應理解為「不可違反的共同要求＋該工作的具體契約」，不是冗長角色扮演。工作包需要：目標、適用限制、來源版本、相依介面、輸出與驗收、未知事項及回查入口。執行者發現缺資料能回查或回報，不必盲從不完整摘要；規劃者也不能任意改寫使用者的限制。

單一模型依序使用不同 context 已能測試核心假設，不必先具備平行推論。獨立核對必須看實際產物與必要來源；同模型換 context 不代表錯誤統計上獨立，能用程式或環境驗證的部分應直接驗證。

## 下一步與研究停止點

延續[重構決策](../design/2026-09-05-constitution-context-reconstruction.md)：先讓既有本地模型在隔離設定下接通「規劃→工作包→執行→核對→整合」。比較清楚指引的單一 context 與分離版本，再分開觀察獨立核對的增益；不能把模型、提示品質及 token 預算同時改變後，全歸功於分工。

保存成果正確率、全域限制遺漏、重試、接續成功、人的介入，以及包含規劃／查資料／核對／整合的總 token 與時間。效益也可能是相同品質下較低監督成本。若主要瓶頸是工具格式或模型能力，先處理該瓶頸，不繼續增加角色。

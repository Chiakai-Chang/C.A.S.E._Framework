# 從漏欄回到完整驗收：復盤與改善建議

日期：2026-09-08。核對基準：`f63822f`。本輪是研究與方案，不修改產品行為、不啟動模型、不推送。

## 先修正問題定義

目標仍是讓本地模型在有限脈絡下完成正確工作，減少使用者監督與重述，不是讓 JSON 好看、增加檢查數或證明分工一定較好。

[上輪證據](../evaluation/2026-09-08-worker-replay-evidence.json)顯示一次 worker-only 重播約 211 秒產出，缺 `maintenance.installerRelated`；它沒有跑 reviewer／integrator，未註冊 executable checks。只能判定該 worker 成果不合格，不能推論完整 CASE 接受錯誤成果，更不能推論 reviewer 已失效。受控 SDK 測試證明指定接線路徑能修復，不代表真實模型一定會修復或所有環境均無問題。

因此上一輪「下一步加可信檢查」需要補正為：**先確認既有驗收如何處理這份已知壞成果，再改善驗收的取得、覆蓋與接入成本**。不另造一套驗收系統，也不放棄仍需驗證的模型接續問題。

## 現行程式實際有什麼

| 層次 | 已有機制 | 未保證的部分 |
|---|---|---|
| 需求與計畫 | `core/contracts.mjs` 檢查 acceptance ID 被 packet checks 引用 | 引用一個涵蓋整案的 ID，不代表每個原始欄位都已納入 |
| 交辦與工具 | `sdk-session.mjs` 角色專用 result schema、限定寫入與 case_result | result schema 管回報，不管寫入檔案的完整結構／內容 |
| 自查與提交 | `runner.mjs` worker 提交前核對檔案／來源及已註冊檢查，失敗保留同 session | 沒有註冊檢查時，不會自動把自然語言轉為正確 validator |
| 獨立核對 | reviewer 讀實際產物，不接 worker 敘述；檢查失敗強制否決；退回 retry | reviewer 仍可能漏驗；本次缺欄樣本尚未實測此路徑 |
| 全域驗收 | integrator 核對整體目標、逐 acceptance 回報 | acceptance 粒度過粗時，逐 ID 回報也可能漏掉子需求 |
| 檢查授權 | `approved-checks.mjs` 按 criterion 篩選；`extension-core.mjs` 以人類確認註冊命令 | 命令具使用者權限、非 sandbox；設定為 session 內資料，接續需重新授權。固定 argv 不等於被執行檔內容不可變 |

## 六個互補面向的改善

### 1. 需求完整性：先避免驗收器也漏題

保留使用者原始需求作為權威。已有 JSON Schema、資料表欄位或測試規格時直接引用並綁定版本，不再由每個角色重新摘要。只有自然語言時，由主責 agent 抽取必要項目並回連來源位置；交辦前核對是否漏掉原要求。這是 AI 的準備工作，不要求人類手填另一份表，也不固定增加模型角色。

不要把「所有欄位正確」一條 acceptance 當成已完整覆蓋；但也不要把每個欄位強制變成獨立任務。子項目可在同一份成果契約中存在，工作仍可是一包。

### 2. 驗收分層：結構、事實與整體價值分開

建議沿用三種互補證據：

- 可機械判定：必要欄位、型別、允許值、數量、唯一性、來源版本、既有測試。從明示規格產生，不把答案塞進模板。
- 來源與語意：欄位值是否由指定來源支持、論述是否正確、例外與矛盾是否處理。由既有獨立 reviewer 核對，測試可覆蓋者直接測。
- 整案：各工作包是否共同達成目標、限制與使用情境。由既有 integration 保留未測與未解項目。

JSON Schema 的 properties 不會自動使欄位必填，須明示 required；禁止額外欄位也必須源自需求，不可對所有任務一律加上。結構合格不代表值正確。[JSON Schema 官方文件](https://json-schema.org/understanding-json-schema/reference/object)

Anthropic 將程式、模型與人類評分區分並建議依工作選擇；其中程式檢查快速但可能脆弱，模型評分需校準。這支持分層而非單一萬能檢查，不是 CASE 已有效的證據。[官方評估方法](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

### 3. 接入與安全：不要為少問一次而自動執行任意程式

先用現有 approved checks 驗證修復閉環，不新增 API。一般化產品候選是**資料式、唯讀、受限的成果檢查**：例如以固定實作核對 JSON 欄位／型別，無 shell、網路、動態程式碼或遠端 schema 載入，並限制檔案大小、巢狀深度與檢查數量。這是待設計能力，不是現況。

代理可以在原授權內整理可追溯的檢查規格；執行者不能自行刪除 required、替換規格或弱化標準。任意命令仍保留現有授權邊界；不能將「檢查」這個名稱當成安全保證。規格有歧義才詢問人類，不把所有低風險檢查逐一交給使用者批准。

### 4. 修復回饋：回到檔案，不是修飾回報

失敗訊息應包含成果路徑、缺陷位置、違反規則、原需求參照；例如缺 `/maintenance/installerRelated`，要求讀指定來源後補齊。不直接提供 oracle 的六個正確值，也不只有「JSON 錯誤」。驗收後綁定成果版本；修復後重驗受影響部分及整體限制，不能靠舊通過狀態結案。

原範圍內可修復就沿用同 session；跨包或缺前置沿用 discovery／planner；授權或目標改變才問人。只有思考而達回覆上限、沒有可用工作紀錄時，不能假稱已保存完整進度；先以外部檔案／觀察接續。模型推理設定另立比較，不跟驗收改動混在一起。

工具錯誤提供具體可行的改善方向，有官方方法支持；但不同模型仍須實測，不保證換一句文案就成功。[Anthropic 工具設計](https://www.anthropic.com/engineering/writing-tools-for-agents)

### 5. 脈絡與成本：不是永遠多拆包、多重讀

先保留一個工作包，不因這次漏欄就拆成四個角色。把當前產物所需的要求與材料交給 worker，reviewer 仍能回看原始需求，避免只核對 planner 摘要。重讀僅在來源更新、疑點、核對成果或壓縮後缺資料時發生。

規劃及執行成本一起算，分階段記錄但不新增任意硬截止。每次重跑既要知道改變了什麼，也要知道保留了哪些有效成果。沒有證據顯示把 context 再壓短就會修好漏欄，不將輸入字數當品質代理指標。

### 6. 泛用性與使用者負擔：按成果選方法

結構化資料用 schema／資料規則，軟體用既有測試，文章／研究用來源支持與審閱準則，操作型工作驗證外部實際狀態。純格式檢查不能假裝核實事實、易讀性或外部操作成功。Skills 教主責 agent 如何選擇／準備／執行這些方法；核心保存狀態與強制可檢查條件，不把 CASE 改成只能處理 JSON 的工具。

不新增通泛根目錄檔名、不綁 GitHub、不固定加角色；優先把已有契約、材料與檢查串好。這延續[使用者指定來源的採納](2026-09-06-user-reference-synthesis.md)與[原始構想對照](2026-09-05-layered-cooperation-direction.md)，沒有撤回即時回饋待辦、自行排除與局部等待的要求。

## 下一步順序與判斷條件

9/9 執行更新：[第一步結果](../evaluation/2026-09-09-review-repair-report.md)為 reviewer 找到缺欄、worker 未寫入即逾時。依下列第 3 點，優先轉向修復執行設定的單因子對照，暫緩第 2 點模型比較及一般化檢查器；保留以下事前順序，不改寫成成功。

1. **確認已有防線**：用已保存的缺欄產物及原需求，走現有 reviewer → repair → integration，無需重新規劃或從頭產出。這是特定修復旅程驗證，不是新的整案成功率樣本。
2. **驗證低成本補強**：在相同材料／工作包／設定下，對照是否接入需求衍生的結構檢查。先用缺欄、錯型別、錯值但結構正確、合法差異、來源變更等離線樣本核對檢查器；正確值由隔離 oracle 在結束後判斷，不回饋答案。模型生成開始前固定兩組及總預算，不能改到出現成功才停。
3. **按結果決定產品改動**：若現有 reviewer 已能修好，保留它並比較提前結構檢查能否降低成本；若漏驗，改善原始需求到驗收的覆蓋；若能發現但模型修不好，聚焦可操作回饋與工作包／模型能力，不再加驗收器。證據顯示接入成本是痛點時，才實作受限資料式檢查。

驗收看完整產物、限制保留、正確修復、總時間／tokens、人工介入與檢查準備成本。一般化前再用不同成果與失敗類型測可遷移性；不以這一欄修好宣稱所有任務有效。模型成本未知就列未知。

獨立研究覆核補充兩個必要界線：若為了測 reviewer 而重建產品狀態，明示「合成恢復起點」，保存原需求／產物雜湊及狀態轉換，不冒稱產品已從 worker-only session 自然續跑。提前檢查的兩組都必須拿到相同完整要求，僅檢查訊號／時機不同，不得只向新組提示已知缺欄。

本輪取捨：研究完成即可交付方案，不因研究請求擅自啟動昂貴模型測試或改變執行／授權行為。外部自我修正與驗收來源見[獨立研究](2026-09-08-acceptance-feedback-sources.md)。

# 回到分層協作：下一步應怎麼做

日期：2026-09-05。性質：依使用者要求的研究與修正建議，**不是已核准的新操作規格，也不是新增功能的完成報告**。本輪不修改產品程式、不啟動模型、不合併或推送。

後續確認：使用者同意本研究建議方向，並要求長期記住原始 CASE 來源，完成後可據此復盤，理解脈絡但不用照抄。已納入 repository 指引與[維護原則](../MAINTENANCE.md#原始構想參照)。方向獲同意不代表建議中的功能已實作，也不改寫本次研究的證據範圍。

## 結論

保留現有共用核心，補回「專案共識與整體規劃 → 清楚交辦 → 有界執行與核對 → 問題回饋 → 調整後接續」的完整關係。以可攜技能和工作資料為框架主體，pi 是第一個自動化接入方式，不是框架本身。不要退回只有長篇指引，也不要另造 agent 平台。

目標仍是讓本地模型在有限 context 下把實際工作做好，減少人類監督、重述與抉擇負擔；強模型也可採用。角色分層不是模型等級排名，不必雲端規劃，也不必同時並行。效益需由成果與總成本驗證。

## 2. 外部研究能支持到哪裡

[外部一手來源筆記](2026-09-05-layered-cooperation-sources.md) 區分原始事實、可採用推論及不可外推。既有[context 研究](2026-09-05-context-isolation-alternatives.md)與[技能證據](2026-09-05-case-value-evidence.md)繼續保留，不重新堆一份文獻清單。

本輪另核對兩篇論文摘要與版本：

- [Lost in the Middle v3](https://arxiv.org/abs/2307.03172v3)：相關資訊的位置會影響受測模型的檢索／問答表現。因此應測必要限制能否被使用，不能只測輸入是否放得下；不能外推目前模型的退化幅度。
- [Towards a Science of Scaling Agent Systems v3](https://arxiv.org/abs/2512.08296v3)：受測架構的相對表現與任務結構相關，多代理不一定更好。因此應比較適合的分工與相依工作，而非增加角色數；摘要中的數值不轉成 CASE 通用門檻。

工程推論：保留分層、持久狀態、按需讀取與獨立核對；調整工作包粒度與回饋方式。研究不要求所有任務有四次模型呼叫，也不要求導入 LangGraph、資料庫、向量庫或背景常駐服務。先重用 AI 工具已有的 session、工具與權限機制。

## 3. 三條路線比較

| 路線 | 能解決什麼 | 主要問題 | 建議 |
|---|---|---|---|
| 回到單份指引＋範本 | 可攜、好理解，容易人工交接 | 未解決已觀察到的不遵循、缺料、假完成及新 context 接線問題 | 作為使用入口，不作唯一機制 |
| 在現有核心補齊分層與回饋 | 保留已測的版本、相依、成果核對及 pi 整合，補實際語意缺口 | 必須避免一份事實在多處被獨立修改 | **推薦** |
| 改用／自建大型多代理平台 | 提供通用排程及持久執行等能力 | 增加設定、遷移及相依，尚無證據是目前瓶頸 | 本輪不採用；將來有具體能力缺口再評估 |

## 4. 補回三層責任，不新增三套重複帳本

| 層次 | 要保存的必要內容 | 誰能決定／改變 |
|---|---|---|
| 專案共識（大憲法） | 長期目的、不可違反限制、資料外流及授權邊界；引用既有專案指引 | 人類掌握目的與授權；AI 可提出修訂，不自行放寬 |
| 整體工作計畫 | 本次成果、階段、任務相依、整體驗收、已知缺口與下一步 | 主責規劃者在既有授權內維護；不把計畫修改等同目標修改 |
| 任務卷宗／工作包（小憲法） | 當前成果、必要指引與來源、允許操作、局部驗收、缺口回報 | 規劃者交辦，執行者可提出修正；不能自行降低標準 |

建議沿用 `.case-agent/` 命名空間與既有工作包能力，不在專案根目錄再建立通泛的 `CASE.md`、`roadmap.md` 等檔案。不因角色對應就複製整份專案規則；保存來源與版本，再組裝實際必需的內容。

**先固定語意，再決定檔案及格式。** 現有 `case` 含契約與多個 packets，不為了文字一一對應而立即更名／搬資料；單卷宗工作也不需要先建額外的多專案管理層。人類總覽可以由權威狀態產生，但不可同時要求修改 JSON 與 Markdown 才算更新成功。新資料若超出目前 manifest 允許項目，必須明示版本遷移，不能偷放檔案後破壞既有讀取。

## 5. 第一優先：讓問題回到正確層次

現在 runner 主要是初次規劃後依序執行；核對失敗可有限重試，但缺前置與整合失敗會停止。核心已有 `revise`，卻不代表 runner 已有重規劃閉環；修訂契約還會保守使全部工作包待重驗。[runner](../../workflow-kit/integrations/pi/runner.mjs)、[狀態核心](../../workflow-kit/skills/case-workflow/scripts/core/state.mjs)

建議提供三種清楚回報：完成、缺料／受阻、計畫變更建議。由協調者判斷後續，不讓執行者直接改全域計畫：

| 發現 | 後續處理 | 人類是否每次介入 |
|---|---|---|
| 產物有具體缺陷、原計畫可行 | 同一包修正，附失敗證據，遵守總預算 | 已授權修正不必再問 |
| 缺少可由現有資料／權限產出的前置成果 | 提出補包，驗證相依及範圍，完成前置後續作 | 不涉及新權限或重要取捨則不必 |
| 缺外部資料、必須捏造才能繼續 | 保留其他有效成果，明示缺什麼及影響 | 需要人提供資料時才問 |
| 各包通過但整體需求未滿足 | 規劃者補上缺口，重新整合；不能反覆問驗收者直到改口 | 原目標內補做不必再問 |
| 需要改目標、授權、預算或不可逆行動 | 提供具體理由與選擇，等待必要決定 | 必須 |

計畫修正不應自動重置預算，也不應把已核對的無關產物全部重做。影響範圍能由相依和來源判定時只使相關部分待重驗；判斷不清則保守處理並說明。對未知副作用不可盲目重播。不要新增固定幾輪的「專家會議」。

## 6. 第二優先：交辦可執行，而不是格式看起來完整

工作包的必要資訊是「做什麼、為何要做、看什麼、能改什麼、如何證明、缺什麼時回報」。執行者開始前給一份短的可觀察操作計畫，檢查材料與驗收是否對得起來；不是要求保存隱藏思考或長篇自我對話。

目前 context builder 會讀入全部標為 required 的文字，超量才停止；這不等於成熟的按需材料供應。[context builder](../../workflow-kit/skills/case-workflow/scripts/core/context.mjs) 建議區分必讀規則／小型材料與可定位的大型資料，後者附用途、版本與查閱位置，提供限定的搜尋、分段或程式讀取能力。必要資訊不得靜默截掉；也不能把所有限制只藏在連結裡。

目前一般 pi extension 沒有設定可信的測試清單。[整合入口](../../workflow-kit/integrations/pi/extension-core.mjs) 要讓本地模型完成真實程式工作，應接上使用者授權的測試工具／檢查設定，保存實際結果；文件與資料任務用相應來源／結構／計算驗證，不以每案都跑程式測試作泛用要求。模型自評不能代替這些證據。

## 7. 經驗、平台與採用體驗

- **經驗只在值得重用時整理。** 原始回報留在卷宗；提煉的教訓帶來源、適用範圍及是否已核對。近期索引只放相關項目，其餘保留可搜尋歷史。不要把「40 行」當研究定律，也不要每次結案強制寫四段無內容復盤。教訓不是新法律，不自動覆寫專案限制。
- **同一協作契約，不承諾相同自動化。** pi 可沿現有整合自動開新 session；其他工具先讀寫相同交辦資料，由其原生能力或明確交接完成。補做「一個工具規劃，另一個工具／本地模型接手」的真實旅程，不能拿 CLI 共用當成完整協作證明。雲端只能收到明確允許的內容，摘要也可能含機密；不得自動雲端 fallback。
- **使用者只交代成果與限制。** 安裝後由 agent 辨識已有指引、整理計畫、派發與接續。init 不要求填一堆表單，不覆寫既有 AGENTS／CLAUDE 等指引，不偷偷改全域設定。模型／資料政策沿用已有設定，只有重要缺口才提問。
- **首頁展示完整旅程。** 先說用途與例子，再說安裝；技術結構、版本沿革及舊研究另頁。人類看精簡總覽，AI 按索引讀工作指引；兩者引用同一份狀態，不各自維護進度。

## 8. 用真正有鑑別力的任務驗證

第一個主案例建議是「將多批來源整理成可追溯的報告與資料產物，含跨檔案規則、可補的缺漏和整體驗收」，例如訂單／價格／退貨／幣別資料的整合。不是再做一個單函式 CSV 轉義。加入可由資料推得的前置成果、不可推測的缺料、來源變更及明確中斷邊界，分開測，不同變因不要一次混成一個失敗。

三個比較條件：A 清楚指令＋AI 工具原生能力；B 同樣工具與資料，加 CASE 指引及工作包；C 同樣條件加狀態檢查、獨立 context、回饋與整合。先以同一本地模型比較，雲地合作另列，不將模型更強的收益算成框架收益。

先用同一主案例的三次配對作工程探測，全部保留；再用未參與調整的另一任務核對。這不是足以證明普遍效果的統計規模，也不應為了完成龐大研究矩陣而延後所有使用。原設計多類任務比較仍有研究價值，但不是每次可用性修正的前置儀式。

共同驗收看真實產物、限制遺漏、假完成、已完成工作是否被重做；同時計入規劃／核對／重試成本和需要人介入的次數。每組都可用相同工具取得資料，不能刻意把基準組塞滿垃圾或拿走必需能力。記錄實際輸入、輸出、模型設定及峰值 context（取不到就標未知），不能只用累計 tokens 假裝是在測 context 壓力。長期記憶效益另用後續任務評估，不能把當次 pass 當成學習成功。

成功可能是相同成果但少一次人類救援，也可能是較多 tokens 換到正確交付；若沒有改善，就修改交辦／回饋或省略無效階段。沒有驗證的方法只標假說。

## 9. 實作前的收斂順序與不做事項

1. 對齊首頁、給人／給 AI 的使用旅程及三層語意；展示同一本地模型可用、也可由別的工具交辦。這是修正定位，不是刪除歷史。
2. 在現有核心補「計畫變更建議 → 範圍檢查 → 前置補包／重新整合 → 接續」，並接上相稱的真實驗證工具。
3. 補必要材料的有界取用、版本引用與經驗索引，讓接手者不重讀全歷史；以主案例驗證回饋及品質，再測跨工具交接。

保留已有狀態、來源雜湊、相依檢查、新 session、失敗紀錄、安裝與遷移保護。不要先增加排程、角色數量、資料庫、模型路由器、訓練流程、雲端協作服務，也不需要推倒全部重寫。不能以新文件的完整度當成產品品質的替代。

**本研究的停止點：** 已能具體指出要保留及補齊的機制，無需擴大文獻搜尋。下一步是依本建議確認修正範圍後實作，不是繼續研究另一套框架。本文件與外部來源筆記加入 MAP；產品能力、版本與既有驗收狀態不因本研究自動改變。

# 驗收與修復回饋：一手來源及採納界線

日期：2026-09-08。目的：改善本地模型的實際交付品質與減少使用者監督，不增加固定角色、審批或無限反思。這是研究建議，不表示產品已實作或模型已證明有效；後續結果可修正本文件的採納判斷。

## 本次證據能回答什麼

[worker-only 重播紀錄](../evaluation/2026-09-08-planning-handoff-report.md)記錄：成果缺少明列的 `maintenance.installerRelated`；當次 preflight 只檢查檔案存在與來源未變，沒有語意檢查，也未執行獨立 reviewer／integrator。因此它證明「執行者一次提交仍可能漏需求」，不證明「完整 CASE 的核對與修復失敗」。不能用框架既有修復介面推定真實模型已會修好，也不能把未執行的核對當成已失效。

## 四份一手來源

本次定向核對原論文全文相關章節與官方文章限制段落；不是最新研究的系統性回顧。論文固定至下列版本，查閱日期均為 2026-09-08。

### 1. 自我修正需要可用的判斷依據，不是多說一次「請檢查」

Huang 等，ICLR 2024，*Large Language Models Cannot Self-Correct Reasoning Yet*，v2，§3–7：研究的「內在自我修正」不使用外部回饋；受測推理任務中修正可能退步。作者亦指出比較應對齊推論成本與初始指引完整度。[原論文](https://arxiv.org/html/2310.01798v2)

採納：優先加入真實可核對的錯誤訊號，不靠無限反思。限制：研究聚焦當時模型與推理任務，不能推成所有模型、所有自查皆無效，更不能直接當成本機模型的因果診斷。

### 2. 回饋可以改善工作，但驗收器本身也會錯

Shinn 等，NeurIPS 2023，*Reflexion: Language Agents with Verbal Reinforcement Learning*，v4，§2、§4.3：框架將評估訊號轉成後續嘗試可用的文字回饋；程式實驗同時呈現自產測試錯誤放行，並指出測試多樣性與完整性限制成果。[原論文](https://arxiv.org/html/2303.11366v4)

採納：回傳能定位、能修復的失敗訊號，另測檢查器能否拒絕已知錯誤成果。限制：通過模型自己產生的測試不等於需求完整；該論文的效益不可移植成 CASE 的成功率承諾。

### 3. 符合結構不等於欄位內容正確

OpenAI，2024-08-06，*Introducing Structured Outputs in the API*，「Limitations and restrictions」：結構化輸出限制格式，仍可能在欄位值內出錯；達輸出上限等情形也需處理。[官方原文](https://openai.com/index/introducing-structured-outputs-in-the-api/)

採納：區分 JSON 可解析、必填／型別完整、來源與語意正確。限制：這是機制界線參考，不代表目前 pi／llama.cpp 接線已啟用相同約束；也不主張為此改換供應商或模型。

### 4. 獨立 session 有用，但不自動產生獨立正確性

Zheng 等，NeurIPS 2023，*Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena*，v4，§3.3–3.4：核對者可能受位置、冗長內容與候選答案誤導；但作者明確說自我偏好效應的資料不足以定論。[原論文](https://arxiv.org/html/2306.05685v4)

採納：reviewer 回到需求與來源驗證，不只同意 worker 摘要。限制：人類偏好評分不是任務正確性驗收；不能把此文說成「同模型一定包庇自己」，也不能因此要求每案換模型或增加評審。

## 本案的設計推論：避免把共同遺漏變成共同通過

以下為結合本案的工程判斷，不是上述論文已驗證的 CASE 實作。

若規劃者遺漏一條需求，而 worker 與 reviewer 都只依同一份不完整檢查表，隔離 session 仍可能共享同一盲點。這裡的「同源風險」指驗收依據共同缺漏，不等同模型自我偏好。

建議把驗收分清三種責任，而非新增三個角色：

| 判斷範圍 | 依據與執行位置 | 不能取代的部分 |
|---|---|---|
| 可機械確認的交付條件 | 使用者明列的必填欄位、型別、檔案；沿用受信任檢查接入點 | 值是否真的來自正確來源 |
| 任務內容與整體目標 | 既有獨立 reviewer 對照原需求、適用來源與真實產物 | 全面形式化保證；來源本身可能不足 |
| 檢查器覆蓋與可靠性 | 開發期預先固定的正確／錯誤反例，另於完整流程做實測 | 真實模型會採納回饋並成功修復的證據 |

不讓 worker 改寫驗收基準以換取通過；不將模型臨時生成的任意程式直接當成受信任命令執行。若明列需求需轉成檢查規格，應保存與原需求的對應，不能只從候選成果倒推出「它已符合的要求」。採用者已有測試或資料 schema 時優先重用，不要求使用者重寫一套。

## 下一個有界驗證建議

1. 先確認現有 core 與 runner 的可信檢查接入，避免重做已有能力；優先讓已保存的缺欄產物走既有 reviewer → repair → integration，分辨目前防線是否真的漏驗。若診斷程式重建起始狀態，明示這是特定修復旅程，不冒稱前次 worker-only session 自然接續。
2. 缺欄回饋指出產物路徑、缺少欄位、對應需求及應回到哪份來源，明示要修正產物後重驗，而非只修改完成摘要。公開結構要求可直接提供；隱藏 oracle 的正確內容不灌入 worker。
3. 再對照提前結構檢查是否有幫助。先用已保存的缺欄產物建立反例；完整正確產物應通過、缺欄與型別錯誤應拒絕，格式完整但內容錯誤不能被宣稱語意通過。在既有權限與總預算內驗證「偵測 → 原 worker 修復 → 重驗」；包含獨立核對，不能只重播 worker 後宣布整案可用。若缺料或發現新工作，走既有回饋佇列；僅新授權或目標取捨才交給使用者。
4. 分列初次產物品質、錯誤偵測、修復是否正確、核對錯誤放行、整案完成與總成本。比較不能讓新組多拿隱藏答案、額外人工提示或未揭露預算，也不要靠反覆抽到成功替代失敗紀錄。

不建議：再加長規劃者指引、固定多輪辯論、無限重試、僅用 JSON 通過代替驗收、把目前缺欄歸咎於 pi 損壞。研究支持的是有依據的回饋閉環；實際改善幅度仍須本專案的真實模型驗證。
